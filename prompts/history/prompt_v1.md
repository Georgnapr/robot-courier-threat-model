# Задание для AI-агента: моделирование угроз (версия 1)

Ты — инженер по безопасности. Построй модель угроз по методологии STRIDE для системы, описанной ниже.
Результат сохрани в файл `artifacts/threat-dragon-model.json` — один JSON-объект в формате OWASP Threat Dragon v2 (раздел 6). После сохранения кратко сообщи, сколько угроз сгенерировано и какие категории STRIDE покрыты.

## 1. Легенда системы

Вариант 5. Система управления автопарком роботов-курьеров.
Централизованная система управления парком из 50 роботов-курьеров в логистическом центре. Система распределяет задания между роботами, оптимизирует маршруты, мониторит состояние каждого робота и взаимодействует с внешними системами WMS и ERP.

Особенности архитектуры:
- микросервисная архитектура с балансировкой нагрузки;
- API-шлюз для маршрутизации запросов к микросервисам;
- база данных заданий и маршрутов PostgreSQL;
- очередь сообщений RabbitMQ для асинхронной обработки;
- интеграция с WMS и ERP по REST API.

Дополнительные требования: автоматическое масштабирование, время отклика API ≤ 200 мс, резервирование критических сервисов.

Критическая функция (назначение задания роботу и построение маршрута) выполняется по схеме TMR: три независимых разнородных канала планирования (CH1 — x86, реализация A; CH2 — ARM, реализация B; CH3 — x86, реализация B) считают решение по одному снимку состояния и отправляют голоса арбитру по UDP/DTLS (порт 8888). Арбитр выбирает решение «2 из 3», подписывает команду ключом из TPM 2.0 и передаёт её шлюзу связи с роботами. Арбитр зарезервирован (active-standby). При отказе одного канала — режим «2 из 2», при отказе двух — выдача новых назначений прекращается, роботам отправляется «пауза».

## 2. Требования к системе

- FR1. Приём заданий из WMS и передача статусов в WMS и ERP через REST API на API-шлюзе (TCP/443); проверка по OpenAPI-схеме; задания ставятся в очередь RabbitMQ.
- FR2. Назначение задания роботу (заряд, загрузка, расстояние) по схеме TMR; фиксация в PostgreSQL.
- FR3. Построение и пересчёт маршрутов по карте логистического центра.
- FR4. Команды роботам (назначение, маршрут, пауза, возврат, экстренная остановка) по TCP/8443 с mTLS; робот выполняет только команды с валидной подписью арбитра.
- FR5. Приём телеметрии 50 роботов по UDP/9999 (DTLS), не реже 1 Гц; оповещение оператора при отказе робота, канала TMR или потере связи более 5 с.
- NFR1. p95 отклика REST API ≤ 200 мс; цикл голосования TMR ≤ 50 мс.
- NFR2. Горизонтальное автомасштабирование (CPU > 70 % или очередь > 1000 сообщений).
- NFR3. TMR «2 из 3» → «2 из 2» → безопасный режим.
- NFR4. Резервирование: арбитр active-standby (≤ 1 с), PostgreSQL primary + синхронная реплика, RabbitMQ ×3, API-шлюз ×2.
- NFR5. TLS 1.3 / DTLS 1.3 на всём трафике; mTLS на сертификатах X.509 внутреннего УЦ с проверкой OCSP; ключи арбитра и роботов в TPM 2.0.
- NFR6. Голос канала содержит номер цикла, метку времени, HMAC-SHA256; арбитр отбрасывает голоса с невалидной подписью, повтором номера цикла или меткой вне окна 50 мс.
- NFR7. OAuth 2.0 (client credentials, JWT) для WMS/ERP, MFA и RBAC для операторов, rate limiting на шлюзе; append-only журнал аудита в SIEM (syslog/TLS, TCP/6514), хранение ≥ 90 суток.

## 4. Требования к угрозам

1. Сгенерируй **от 16 до 20** уникальных угроз.
2. Покрой **все 6 категорий STRIDE**, в каждой категории не меньше 2 угроз.
3. Каждая угроза привязана к **существующей** ячейке DFD: поле `target` = id элемента или потока, и та же угроза лежит в `data.threats` этой ячейки.
4. Не создавай двух угроз с одинаковыми `target` и `stride_category`, если сценарии не отличаются по сути.
5. Обязательно рассмотри: голоса каналов TMR, сам арбитр и его резерв, команды роботам, телеметрию, внешний REST API, PostgreSQL, RabbitMQ, журнал аудита, УЦ.
6. Мера защиты должна быть **технической и конкретной**: протокол, библиотека, механизм, параметр.
   - Плохо: «использовать шифрование», «усилить защиту», «настроить доступ».
   - Хорошо: «mTLS с сертификатами X.509 внутреннего УЦ и проверкой отзыва по OCSP stapling, TLS 1.3 only».
7. Для каждой угрозы укажи хотя бы один реальный идентификатор CWE, соответствующий сути угрозы. Всего — не менее 10 разных CWE на модель.
8. `likelihood` и `impact_score` — целые от 1 до 5; `severity` — Critical / High / Medium / Low (в ячейке Threat Dragon: Critical → High).
9. В `invariants` перечисли инварианты из раздела 5, которые нарушает угроза.

## 5. Инварианты безопасности

- INV1. Ни одна команда управления не выполняется роботом без успешной mTLS-аутентификации и проверки подписи арбитра.
- INV2. Телеметрия не содержит конфиденциальных данных и не может инициировать команды управления.
- INV3. Арбитр TMR принимает только голоса с валидной подписью, уникальным номером цикла и меткой времени в допустимом окне.
- INV4. При отказе одного канала TMR система продолжает работу («2 из 2»); при отказе двух — переходит в безопасный режим.
- INV5. Внешние системы не имеют прямого сетевого доступа к микросервисам, БД и брокеру — только через API-шлюз.
- INV6. Журнал аудита ведётся только на добавление и не может быть изменён ни одним сервисом системы.

```json
  "detail": {
    "contributors": [], "reviewer": "", "diagramTop": 1, "threatTop": 18,
    "diagrams": [{
      "version": "2.3.0", "id": 0, "title": "DFD уровня 0", "description": "", "diagramType": "STRIDE",
      "thumbnail": "./public/content/images/thumbnail.stride.jpg",
      "cells": [ ...границы, элементы, потоки... ]
    }]
  },
  "threats": [ ...плоский список всех угроз... ]

```

### Ячейки `cells`

Граница доверия (`zIndex: -1`):
```json
{"id": "TB-TMR", "shape": "trust-boundary-box", "zIndex": -1,
 "position": {"x": 1610, "y": 20}, "size": {"width": 470, "height": 600},
 "attrs": {"label": {"text": "VLAN 30 — контур TMR, 10.0.30.0/24"}},
 "data": {"type": "tm.BoundaryBox", "name": "VLAN 30 — контур TMR, 10.0.30.0/24", "isTrustBoundary": true, "hasOpenThreats": false}}
```

Процесс (`process`, 130 × 130, `tm.Process`), внешняя сущность (`actor`, 160 × 80, `tm.Actor`), хранилище (`store`, 170 × 90, `tm.Store`). Текст — название и IP через `\n`. Если у ячейки есть угрозы, `hasOpenThreats: true` и обводка `red`, иначе `#333333`:
```json
{"id": "P-ARB", "shape": "process", "zIndex": 10,
 "position": {"x": 1875, "y": 255}, "size": {"width": 130, "height": 130},
 "attrs": {"text": {"text": "Арбитр TMR\n(основной)\n10.0.30.100"}, "body": {"stroke": "red", "strokeWidth": 2.5, "strokeDasharray": ""}},
 "data": {"type": "tm.Process", "name": "Арбитр TMR (основной)", "description": "Голосование 2 из 3, подпись команд ключом из TPM 2.0",
          "hasOpenThreats": true, "threats": [ ...угрозы этой ячейки в формате ниже... ]}}
```
Для `store` вместо `body` используются `topLine` и `bottomLine` с теми же полями.

Поток (`flow`, `tm.Flow`). Метка — id потока и транспорт/порт; в `protocol` — транспорт/порт, протокол и защита:

```json
          "hasOpenThreats": true, "threats": [ ... ]}}
```

### Угроза в ячейке (`data.threats[]`)

```json
{"id": "TM-01", "threatId": "TM-01", "number": 1, "title": "TM-01. Подделка голоса канала TMR",
 "type": "Spoofing", "modelType": "STRIDE", "status": "Open", "severity": "High", "score": "10",
 "description": "Сценарий... Последствия: ... CWE: CWE-290, CWE-345",

```
`type` — строго одно из: `Spoofing`, `Tampering`, `Repudiation`, `Information disclosure`, `Denial of service`, `Elevation of privilege`. `score` — likelihood × impact_score строкой.

### Правила

- В `cells` должны быть **все** 9 границ, 20 элементов и 31 поток из раздела 3 (плюс добавленные тобой).
- Число угроз в корневом `threats` равно суммарному числу угроз во всех `data.threats`; id совпадают.
- Файл — валидный JSON без комментариев. Не заявляй в итоговом сообщении того, чего нет в файле.
