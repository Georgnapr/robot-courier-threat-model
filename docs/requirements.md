# Требования к системе

**Вариант 5.** Система управления автопарком роботов-курьеров

Централизованная система управления парком из 50 роботов-курьеров в логистическом центре: распределение заданий, оптимизация маршрутов, мониторинг состояния роботов, интеграция с WMS и ERP.

## Принятые протоколы и порты

| Поток | Протокол / порт | Основание |
|---|---|---|
| WMS, ERP, АРМ оператора → API-шлюз | HTTPS (TCP/443, TLS 1.3) | Прил. 1: REST API, TCP/TLS 443 |
| Команды управления → роботы | TCP/8443, mTLS | Прил. 1: критичные команды TCP/TLS 8443 |
| Межсервисные вызовы (шлюз → микросервисы) | TCP/8443, mTLS | Прил. 1: mTLS |
| Голоса каналов TMR → арбитр | UDP/8888, DTLS 1.3 | Прил. 1: голосование UDP/DTLS 8888 |
| Телеметрия роботов → сервис мониторинга | UDP/9999, DTLS 1.3 | Прил. 1: телеметрия UDP/DTLS 9999 |
| Сервисы → PostgreSQL | TCP/5432, TLS | Легенда: БД заданий и маршрутов |
| Сервисы → RabbitMQ | AMQPS, TCP/5671 | Легенда: очередь сообщений |
| Журналы → SIEM | syslog/TLS, TCP/6514 | NFR7 |

## Функциональные требования

| № | Требование | Категория | Источник | Критерий проверки |
|---|---|---|---|---|
| FR1 | Интеграционный сервис принимает задания на доставку из WMS и передаёт статусы выполнения в WMS и ERP через REST API на API-шлюзе (TCP/443). Входящие запросы проверяются по OpenAPI-схеме, принятые задания ставятся в очередь RabbitMQ. | Интеграция | Легенда | Задание из WMS появляется в очереди и в БД; запрос с нарушением схемы отклоняется с HTTP 400 |
| FR2 | Сервис диспетчеризации назначает каждое задание конкретному роботу с учётом заряда батареи, текущей загрузки и расстояния до точки погрузки. Решение о назначении принимается по схеме TMR (см. NFR3) и сохраняется в PostgreSQL. | Диспетчеризация | Легенда | Назначение выдаётся только после голосования арбитра и фиксируется в БД с номером цикла |
| FR3 | Сервис планирования строит маршрут робота по карте логистического центра с учётом занятых участков и маршрутов других роботов и пересчитывает его при блокировке участка. | Маршрутизация | Легенда | При блокировке участка новый маршрут выдаётся роботу без проезда через этот участок |
| FR4 | Система передаёт роботам команды управления (назначение задания, маршрут, пауза, возврат на базу, экстренная остановка) по TCP/8443 с mTLS. Робот выполняет только команды, прошедшие проверку сертификата и подписи арбитра. | Управление / безопасность | Легенда, Прил. 1 | Команда без валидного сертификата или подписи арбитра отклоняется роботом и фиксируется в журнале |
| FR5 | Сервис мониторинга принимает телеметрию всех 50 роботов (координаты в системе координат склада, заряд, скорость, коды ошибок) по UDP/9999 с частотой не менее 1 Гц и оповещает оператора об отказе робота, отказе канала TMR или потере связи с роботом более 5 с. | Мониторинг | Легенда, Прил. 1 | Отключение робота приводит к оповещению оператора не позднее чем через 5 с |

## Нефункциональные требования

| № | Требование | Категория | Источник | Критерий проверки |
|---|---|---|---|---|
| NFR1 | Время отклика REST API (p95) не превышает 200 мс при штатной нагрузке; цикл голосования TMR по одному назначению не превышает 50 мс. | Производительность | Легенда | Нагрузочный тест: p95 ≤ 200 мс; метрика длительности цикла голосования ≤ 50 мс |
| NFR2 | Сервисы диспетчеризации, планирования, мониторинга и интеграции масштабируются горизонтально и автоматически: новая реплика добавляется при загрузке CPU более 70 % или длине очереди RabbitMQ более 1000 сообщений, без остановки обслуживания. | Масштабируемость | Легенда | При росте нагрузки число реплик увеличивается без ошибок на стороне клиентов API |
| NFR3 | Решение о назначении задания и маршруте формируют три независимых экземпляра сервиса планирования (каналы TMR) по одному снимку состояния и детерминированному алгоритму. Арбитр принимает решение по принципу «2 из 3». При отказе одного канала система работает в режиме «2 из 2». При отказе двух каналов новые назначения не выдаются, роботы получают команду «пауза». | Отказоустойчивость | Легенда, методичка (TMR) | Отключение одного канала не прерывает выдачу назначений; отключение двух каналов переводит систему в безопасный режим |
| NFR4 | Критические сервисы резервируются: арбитр работает по схеме active-standby с переключением не более 1 с, PostgreSQL — ведущий узел с синхронной репликой и автоматическим переключением, RabbitMQ — кластер из трёх узлов с кворумными очередями, API-шлюз — не менее двух экземпляров за балансировщиком. | Резервирование | Легенда | Отказ любого одного узла не приводит к потере принятых заданий и недоступности API |
| NFR5 | Весь сетевой трафик шифруется: TLS 1.3 для TCP-потоков, DTLS 1.3 для UDP-потоков. Каналы TMR, арбитр, сервисы и роботы взаимно аутентифицируются по сертификатам X.509 внутреннего УЦ с проверкой отзыва (OCSP). Закрытые ключи арбитра и роботов хранятся в TPM 2.0. | Безопасность | Прил. 1 | В сети нет открытого трафика; узел с отозванным сертификатом не устанавливает соединение |
| NFR6 | Каждый голос канала TMR содержит номер цикла, метку времени и подпись канала (HMAC-SHA256 на ключе канала). Арбитр отбрасывает голоса с невалидной подписью, повторяющимся номером цикла или меткой времени вне окна 50 мс. | Безопасность (целостность TMR) | Методичка (инвариант 3) | Повторно отправленный или изменённый голос отклоняется и регистрируется как событие безопасности |
| NFR7 | Доступ к API разграничен: внешние системы (WMS, ERP) аутентифицируются по OAuth 2.0 (client credentials, JWT), операторы — с MFA и ролевой моделью (оператор, администратор). На шлюзе действует ограничение частоты запросов. Команды, назначения и события безопасности записываются в журнал только на добавление и передаются в SIEM по syslog/TLS (TCP/6514); срок хранения не менее 90 суток. | Безопасность (доступ, аудит) | STRIDE (S, R, E) | Запрос без токена отклоняется с HTTP 401; запись журнала нельзя изменить; события доступны в SIEM |

## Инварианты безопасности

Используются в промпте для GA и при проверке верификаторами.

| № | Инвариант | Основание |
|---|---|---|
| INV1 | Ни одна команда управления не выполняется роботом без успешной mTLS-аутентификации и проверки подписи арбитра | FR4, NFR5 |
| INV2 | Телеметрия не содержит конфиденциальных данных (сведений о заказах и клиентах, ключей, учётных данных) и не может инициировать команды управления | FR5, методичка |
| INV3 | Арбитр TMR принимает только голоса с валидной подписью, уникальным номером цикла и меткой времени в допустимом окне | NFR6, методичка |
| INV4 | При отказе одного канала TMR система продолжает работу («2 из 2»); при отказе двух — переходит в безопасный режим | NFR3, методичка |
| INV5 | Внешние системы не имеют прямого сетевого доступа к микросервисам, БД и брокеру — только через API-шлюз | FR1, NFR7 |
| INV6 | Журнал аудита ведётся только на добавление и не может быть изменён ни одним сервисом системы | NFR7 |
